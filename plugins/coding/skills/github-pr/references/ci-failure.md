# CI の失敗を読む

PR の CI が落ちたときに読みます。読み取りだけで原因を絞り、直す手順を1つ提案します。

## 手順

1. 失敗したチェックを特定します（すぐ実行）。`gh pr checks <番号>` の `fail` の行が対象です。リンクの `runs/<run-id>` が、実行の番号です。
2. 失敗した箇所のログを読みます。`gh run view <run-id> --log-failed` は、失敗したステップのログを `ジョブ名 <TAB> ステップ名 <TAB> 時刻 メッセージ` の形で出します。長いので、末尾から読みます（`| tail -n 80`）。原因は、多くの場合、末尾の `##[error]` の近くにあります。ログには、伏せきれていない認証情報が残ることがあります（GitHub が伏せるのは、登録された secret だけで、加工された値や未登録の認証情報は伏せません）。引用する前に、トークンやパスワードらしき文字列がないかを見て、あれば伏せます。
3. 原因を一言で伝えます。引用する行は数行に絞ります。

## 原因の見分け方

| ログの様子 | 原因 | 次の一手 |
| :- | :- | :- |
| テストやリンタのメッセージ、`exit code 1` | コードの問題 | 手元の変更を壊さないよう読み取りの点検（`CONTRIBUTING.md` のタスク）から実行して再現し、直して `push` する |
| `403`、`Resource not accessible` | 権限の問題（トークンの権限、フォークからの PR） | ワークフローの `permissions` は `github-actions` に任せ、利用者に状況を伝える |
| `log not found`（`--log-failed`）。`gh run view <run-id>` に `workflow file issue` と出る | ワークフローの定義の不具合 | `.github/workflows/` の構文や設定の問題なので、`github-actions` に進む |
| ネットワークの一時的なエラーなど、ログから一時的と見えるとき | 一時的な失敗の可能性 | 失敗したジョブだけを再実行する（`gh run rerun <run-id> --failed`。確認を取る） |
