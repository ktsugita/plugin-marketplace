# GitHub Issue の案内

GitHub 初学者（Git の基本操作は一部分かるが、GitHub の Issue と Pull Request の運用に慣れていない利用者）が Issue を使うのを助けます。

操作は2段階で扱います。読み取りはすぐ実行し、書き込みは、どれも他の人に見えるので、確認を取ってから実行します。

次の3語を、この意味で使います。

- **確認を取る**: 実行するコマンド、変わること、戻せないことを示し、利用者の返事を待つこと。
- **区切り**: 作業の節目（Issue を読んだ、作った、似た Issue を見つけた、など）。
- **兆候**: 迷いや失敗のしるし。エラー出力の貼り付け、「分からない」「どうすれば」、同じ操作の繰り返し、用語の取り違え。

**提示だけ**は `git-config` と同じ意味です（コマンドを実行せず、利用者に示すだけにすること）。

## 準備と前提

- リポジトリの決まりを先に読みます（読み取りだけ）: `.github/ISSUE_TEMPLATE/`、`CONTRIBUTING.md`、`AGENTS.md`、`docs/agents/` 配下。あれば、この skill の既定より先に従います。
- 最初の書き込みの直前に、`gh auth status` で認証を、`gh repo view --json nameWithOwner --jq .nameWithOwner` で送り先のリポジトリを確かめます。複数のリモートがあるときは、`gh repo set-default` か `-R <owner>/<repo>` で送り先を決めます。
- `gh auth login` は対話式なので、利用者が自分で実行するコマンドとして提示だけにします（Claude Code では `! gh auth login` と入力すると、その場で実行できます）。設定の不具合は `git-config` に任せます。
- `gh auth token` と `gh auth status --show-token` は、秘密が出るので避けます。

## 区切りと次の一手

次の一手は1つだけ、理由を1文つけて提案します。実行は、利用者が頷いてからです。

| 区切り | 次の一手 |
| :- | :- |
| Issue を読んだ（取り組む） | 後から結びつけやすいよう、Issue 番号を名前に含めた作業用のブランチを切る（`git` へ）。 |
| Issue を作った | URL を示し、ラベルや担当は聞かれたときだけ扱う。 |
| 似た Issue を見つけた | 同じ話題を1か所に集めるため、新しく作らず、既存にコメントする。 |
| 範囲が大きいと分かった | 分けることを提案する。そのリポジトリのメンテナー（管理者）で、`mattpocock-skills` が入っているなら、`/mattpocock-skills:to-tickets` を自分で実行するよう案内する。 |
| 作業が終わった | PR を作り（`github-pr` へ）、デフォルトブランチ向けの PR なら、本文に `Closes #番号` を入れて、マージで Issue が閉じるようにする。 |

兆候があるときは、説明を厚くします。用語は初出で1文だけ説明し、利用者がその用語を正しく使っているなら省きます。

## 確認を取る操作

| 段階 | 操作 |
| :- | :- |
| すぐ実行する | `gh issue list`、`gh issue view`、`gh issue status`、`--search` による検索、`gh label list` |
| 確認を取ってから実行する | `gh issue create`、`comment`（`--edit-last` を含む）、`edit`（タイトル・本文・ラベル・担当）、`close`、`reopen` |

`delete`、`transfer`、`lock`、`pin` は勧めません。確認では、送り先のリポジトリ、タイトル、本文（コメントなら番号と本文）を見せます。

## 場面ごとの手順

### 探す、読む

- 検索: `gh issue list --search "<キーワード>" --state all`。閉じた Issue も探します。
- 読む: 本文は `gh issue view <番号>`、コメントは `gh issue view <番号> --comments` です。`--comments` はコメントだけを出し（コメントがなければ何も出ません）、本文は出さないので、両方を実行して、要点を伝えます。

### 作る

1. 重複を調べます（上の検索）。似たものがあれば、新しく作らず、既存へのコメントを提案します。
2. 決まりを確かめます。Issue テンプレートがあれば、そのファイルを読み、項目を埋めます。
3. なければ、既定の骨格で下書きします。バグは「何が起きたか / 期待した動き / 再現手順 / 環境」。要望は「背景 / やりたいこと / 完了の条件」。足りない要素は、利用者に1つずつ聞きます。
4. 言語は、既存の Issue（`gh issue list --state all --limit 5`）に合わせます。
5. 下書きから、トークン、パスワード、鍵などの認証情報を、確認を待たずに必ず取り除きます。個人情報や非公開の情報が入っていれば、公開してよいかを利用者に確かめます。
6. 送り先のリポジトリ、タイトル、本文を見せて、確認を取ります。
7. 本文を一時ファイルに書き、`gh issue create --title "<タイトル>" --body-file <ファイル>` で作ります。`--body-file` なら、複数行の本文が壊れません。`--title` と `--body`（または `--body-file`）がないと、対話式のプロンプトが出て止まります。

### コメントする、閉じる

- コメント: 下書きを見せて確認を取り、`gh issue comment <番号> --body-file <ファイル>`。
- 閉じる: 紐づく PR があれば、PR の `Closes #番号` に任せます。PR がないときだけ、確認を取って `gh issue close <番号> --reason "<種別>" --comment "<理由>"`。種別は `completed`、`not planned`、`duplicate` から選び、`not planned` のように空白を含む値も、引用符で囲みます。
- 閉じた Issue をもう一度開くときは `gh issue reopen <番号>`（確認を取る）。

### PR と結びつける

PR の本文に `Closes #番号`（または `Fixes`、`Resolves`）を書くと、マージで Issue が閉じます。ただし、キーワードが働くのは、PR がリポジトリのデフォルトブランチ向けのときだけです。別のブランチ向けの PR や、閉じたくない関連づけには、`Refs #番号` を使います。閉じるのは `gh issue close` で行います。本文を書くのは `github-pr` です。

### 扱う範囲

ラベル、担当、マイルストーン、プロジェクトは、利用者が言ったときだけ設定し、ラベルは `gh label list` にあるものから選びます。サブ Issue、依存関係、Issue テンプレートの作成は、この skill の範囲外です。

## 他の skill への案内

- メンテナー（管理者）向け: `mattpocock-skills` が入っているときは、ラベルで状態を動かすために、`/mattpocock-skills:triage` を自分で実行してください。
