# コンフリクトの解消

`merge` や `pull` で、同じ場所を両側が変えたときに出ます。`pull.rebase` が有効なら `rebase` の途中で、`stash pop` でも出ます。`git status` に `both modified:` と出たファイルが対象です。「種類を確かめる」で手順を決め、1ファイルずつ進めます。

## 読み方

ファイルには、次の印が入っています。

```
<<<<<<< HEAD
手元の側の内容
=======
取り込む側の内容
>>>>>>> origin/main
```

`merge.conflictStyle` が `zdiff3` なら、`|||||||` の下に、共通の祖先の内容も出ます。両側が、祖先から何を変えたかを見分けられます。

## 種類を確かめる

`git status` の表示で、手順が分かれます。

| 表示 | 内容 | 進め方 |
| :- | :- | :- |
| `both modified`、`both added` | 両側が同じ場所を変えた。テキストなら、ファイルに印が入る | 下の手順 |
| `deleted by us`、`deleted by them` | 片側が削除し、片側が変更した。印は入らない | ファイルを残すか削除するかを、利用者に聞く。残すなら `git add <ファイル>`、削除するなら `git rm <ファイル>` |
| バイナリ（画像など） | 印は入らない | どちらの版を採るかを、利用者に聞く。`git checkout --ours <ファイル>`（手元の側）または `git checkout --theirs <ファイル>`（取り込む側）で選び、`git add <ファイル>`。選ばなかった側の変更は、ファイル全体で捨てるので、何が失われるかを説明し、確認を取る。`restore --ours` / `--theirs` でも同じ。`rebase` の途中では、`--ours` と `--theirs` の指す側が逆になる |

## 手順

1. `git status` で、コンフリクトしたファイルの一覧を見せます（すぐ実行）。
2. ファイルを1つ開き、両側が何を変えたかを、利用者の言葉で説明します。
3. 解消の案を1つ示します。どちらかの側をそのまま採るか、両方を組み合わせるか。意図が読み取れないときは、利用者に聞きます。
4. 利用者が頷いたら、印（`<<<<<<<`、`=======`、`>>>>>>>`）を消して、ファイルを仕上げます。
5. `git add <ファイル>` で、解消したことを伝えます（説明してから実行）。
6. すべてのファイルが済んだら、`git status` で残りがないことと、`git diff --cached --check` で、`add` した内容に印が残っていないことを確かめ、テストやビルドがあれば実行します。
7. 締めます（下の表）。メッセージは、Git が用意したものを、そのまま使ってかまいません。

| 途中の操作 | 締め | やめるとき（確認を取る） |
| :- | :- | :- |
| `merge`、`pull` | `git commit`（または `git merge --continue`） | `git merge --abort` |
| `rebase` | `git rebase --continue` | `git rebase --abort` |
| `stash pop` | 不要（commit しない）。仕上がりを確かめたあと、stash は残っているので、不要なら `git stash drop`（確認を取る） | 不要（`git restore` で戻す場合は、確認を取る） |

## 途中でやめたいとき

`merge --abort` と `rebase --abort` は、操作を始める前の状態に戻します。解消のために編集した内容は失われるので、確認を取ります。
